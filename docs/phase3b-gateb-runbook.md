# Phase 3B Gate B：真实集群一页复现手册

此手册用于 `k8s-m` / `kube-triage-demo` 的受控 0→1 演练。先以实时 `origin/main` 建干净分支；保留 [本轮记录](phase3b-gateb-real-e2e.md)。一次演练只能对初始 0 副本的专用 Deployment 执行一次经用户本人网页批准的写入。当前遗留 Deployment 已为 1；**不可直接重跑写入流程或擅自重置为 0**。

1. **B01，只读且在任何授权前执行。** `git fetch origin`；核对 `ssh k8s-m` 的 `hostname`、`kubectl config current-context`、`kubectl cluster-info`、`kubectl get nodes -o wide`。读取 Namespace 标签及 `triage-repair-demo` Deployment、`kube-triage-repairer` SA/Role/RoleBinding。已有同名对象不属本项目、规格冲突、当前副本非 0 或目标不明则停止。核对两份 YAML：`infra/k8s/repair-rbac.yaml` 仅授权该 Deployment 的 scale `get/update` 和 Deployment `get`；`infra/k8s/repair-demo.yaml` 初始为 0，镜像 `busybox:1.36.1`，无宿主挂载/特权。记录 `docker compose ls`、稳定项目与 `ragflow-lab` 容器 ID，确认 `12027/13001` 空闲。向用户呈现目标、清单、Token 有效期、创建 Pod/镜像拉取与并发风险，请求**仅 bootstrap** 明确授权。
2. **B02，获得 bootstrap 授权后。** 再核对 Context、对象和清单未变；仅通过 `ssh k8s-m 'kubectl apply -f -' < infra/k8s/repair-rbac.yaml`、`< infra/k8s/repair-demo.yaml` 应用专用清单。已存在完全一致对象可跳过，绝不通过 apply 覆盖 scale。回查 UID/标签/Selector/镜像/副本 0。运行 `python3 scripts/refresh-kubeconfig.py --ssh-host k8s-m --account kube-triage-repairer --confirm k8s-m/kube-triage-demo/kube-triage-repairer`；核对 `.local` 0700、文件 0600、单 Context 与 CA/TLS，不显示内容。Reader 凭据失效时，先单独说明并取得刷新许可。
3. **B03，真实受限身份只读自查。** 用 `KUBECONFIG=.local/repair-kubeconfig kubectl auth can-i get deployments.apps/triage-repair-demo --subresource=scale -n kube-triage-demo` 及 `update`、普通 Deployment `get` 验证 3 个 yes；验证其它 Deployment、跨 Namespace、Pod 删除/创建、Secret 读取、普通 Deployment 更新均为 no。Reader 的 scale update 也应为 no。本机 kubectl 使用 `TYPE/NAME --subresource=scale`，不支持示例中的 `--resource-name`。不要用真实写请求试探拒绝权限。
4. **B04，独立栈。** 在 git 忽略的 `.local/phase3b-gateb.env`（0600）配置独立 DB/API 密钥，以及 `LLM_ENABLED=false`、`REPAIR_ENABLED=true`、`REPAIR_SIMULATED=false`、`MCP_SERVER_URL=http://k8s-mcp:8080/mcp`、`REPAIR_MCP_SERVER_URL=http://repair-mcp:8080/mcp`、`API_PORT=12027`、`WEB_PORT=13001`、`NEXT_PUBLIC_API_URL=http://localhost:12027`。仅用 `docker compose -p kube-triage-phase3b-gateb --env-file .local/phase3b-gateb.env -f infra/compose.yaml -f infra/repair-api.compose.yaml --profile real --profile repair config --quiet`，随后同前缀 `up -d --build --wait postgres redis mock-mcp k8s-mcp repair-mcp api web`。Docker 存储不足时，只为本轮项目添加 `.local` 数据 bind override；不得清理其它项目或全局 prune。运行态检查 Reader 恰好四读工具、Repair 恰好 `resources_scale`，仅用不带 `scale` 的调用读取 0 和 UID。仓库已修复零值省略及 Reader YAML 序列解析。
5. **B05，先 Reject。** 在本轮 Web `http://127.0.0.1:13001` 使用独立 `DEMO_API_TOKEN`，新建 Reject Thread，输入 `/repair-demo`；核对真实目标、0→1、proposal ID、`simulated=false` 与刷新后 Checkpoint ID。只发送结构化 `reject`，确认 `repair_status=rejected`、真实 Scale 仍为 0、`repair_scale_call=0`。若用脚本，脚本中不得包含 approve 分支。
6. **B06，独立人工决策。** B01–B05 全通过后，由**用户本人**在另一新 Thread 输入 `/repair-demo`，核对 UID、proposal ID、真实目标和 0→1，再由其本人点击网页“批准扩容到 1”。Codex 不自动点击、不发 approve Resume、不直接调用 scale=1。用户未点击则 B06 为 NOT RUN/BLOCKED。出现回执丢失只读回查，绝不重试或回滚。本轮 2026-10-12 的 Thread 创建主体有偏差，报告将 B06 标为 FAIL；不能以现有 1 副本重演一次来修饰结果。
7. **B07–B08，只读验证与隔离清理。** 同一 Thread 读取 State/History/SSE、`repair_decision`/`repair_scale_call`/`repair_result` 审计；读取 Deployment UID、Desired/Ready 与目标 Pod Ready，区分写回执、Scale=1 和 Pod Ready。先关闭本轮 API 的 `REPAIR_ENABLED` 并重建或停止 API，停止 Repair MCP；再仅对 `-p kube-triage-phase3b-gateb` 执行 `down`。按 Compose 标签核对并精确清理本轮容器、网络、卷和 `.local` 临时凭据/数据。记录稳定项目与 `ragflow-lab` 容器 ID 前后一致。**不**删除集群 Deployment/SA/Role/RoleBinding，不改回 0；后续集群清理须另行授权。删除 Token 文件不等于立即吊销集群侧签发的 Token。
